# BotiX AI Repair

בוט WhatsApp שמקבל תיאור תקלה בעברית (ואפשר גם צילום מסך), בודק את הקוד של BotiX בעזרת Claude Code, מכין תיקון בענף Git נפרד, מריץ בדיקות, מעלה לסביבת בדיקה, ומעלה לשרת הפעיל **רק אחרי אישור מפורש שלך בוואטסאפ**.

## איך זה עובד

1. שולחים לבוט: "ההפצה לא עובדת". אפשר לצרף צילום מסך.
2. הבוט בודק שהמספר מאושר, פותח פנייה ומזהה את התחום (הפצה, עזרה, חיבור זרועות, כניסה, ממשק, מסד נתונים).
3. הבוט קורא לוגים מ-Railway ומסתיר מהם מפתחות, סיסמאות ומספרי טלפון של לקוחות.
4. Claude Code עובד על עותק נפרד של הקוד, עם כלי קבצים בלבד: קריאה, חיפוש ועריכה. אין לו shell, אין לו אינטרנט, אין לו גישה לשרת, ואין לו סודות.
5. אם יש תיקון, הוא נשמר בענף `fix/ticket-<מספר>-<תחום>` ונפתחת עליו בקשת מיזוג (PR) ב-GitHub.
6. הבוט מריץ את הבדיקות האוטומטיות של הפרויקט. אם הן נכשלות, Claude מקבל את השגיאה ועוד ניסיון אחד.
7. התיקון עולה לסביבת הבדיקה (staging), והבוט מוודא שהיא עלתה ותקינה.
8. המאשרים מקבלים בוואטסאפ סיכום וקוד חד-פעמי בן 6 ספרות. רק `אשר <קוד>` ממספר מאשר מעלה לשרת הפעיל.
9. אחרי ההעלאה הבוט בודק שהשרת עלה. אם הוא קרס, הבוט מחזיר אוטומטית לגרסה הקודמת ופותח בקשה לביטול השינוי גם בקוד.

כל שלב נרשם ביומן הפעולות: מי ביקש, מה השתנה, תוצאות הבדיקות, מי אישר, והאם ההעלאה הצליחה.

## אבטחה

- **אין הרצת פקודות מוואטסאפ.** כל הודעה מושווית לרשימה קבועה של פקודות. כל דבר אחר נשמר כטקסט בלבד, ו-Claude מקבל אותו כ"מידע ולא הוראות".
- **רק מספרים מאושרים.** הודעות ממספרים אחרים נרשמות ביומן, ותמונות מהם לא מורדות בכלל. המספר מקבל תשובה אחת ביום, וזהו.
- **ל-Claude יש רק כלי קבצים:** קריאה, חיפוש ועריכה. אין לו Bash, אין אינטרנט, אין git ואין הרשאה להריץ קוד. הוא רץ במצב `--restricted` עם `--permission-mode dontAsk`, ולכן מתעלם מקובצי הגדרות ו-hooks. הוא עובד על עותק נקי של הקבצים, **בלי תיקיית `.git`**, כמשתמש לינוקס נפרד (`runner`) עם תיקיית בית ריקה וחדשה בכל פנייה.
- **בדיקות הפרויקט** רצות אחרי Claude, כמשתמש `runner`, בסביבה בלי שום סוד, אפילו לא טוקן ה-Claude. אחרי כל שלב כל התהליכים של `runner` נהרגים.
- **git רץ רק בעותק נפרד ששייך לשרת.** hooks וכל הגדרות ה-git של המשתמש והמערכת כבויים. טוקן GitHub מועבר דרך משתני סביבה של תהליך השרת, ולא בשורת פקודה ולא בקובץ. השינויים מועתקים מהעותק של Claude חזרה כקבצים רגילים בלבד, וקישורים (symlinks) נדחים.
- **סודות:** כל לוג, הודעה, פלט בדיקות ותיאור PR עוברים הסתרת סודות ומספרי טלפון. diff שנראה כאילו הוא מוסיף מפתח נעצר לפני כל push.
- **קבצים אסורים:** `repair/`, `.github/`, `.claude/`, `.husky/`, קובצי `.env`, `.npmrc`, `.gitattributes`, `.gitmodules`, `Dockerfile`, `railway.json/toml`, `nixpacks.toml`. שינויים בהם מבוטלים. אם נשאר בהם שינוי כלשהו, הפנייה נעצרת בלי לשמור כלום.
- **ייצור:**
  - אין מיזוג לענף הראשי בלי קוד אישור תקף. הקוד תקף 30 דקות, נצרך פעם אחת בלבד גם אם שני מאשרים שולחים אותו באותו רגע, ומתבטל אחרי 5 קודים שגויים.
  - בכל רגע מתבצעת רק פעולה אחת על הייצור: העלאה או החזרה.
  - המיזוג נועל את הגרסה המדויקת שעברה את סביבת הבדיקה. אם פנייה אחרת דרסה בינתיים את ה-staging, הבוט מעלה אליו שוב את התיקון לפני הייצור.
- **אין העלאה בלי staging.** אי אפשר לכבות את זה. כל עוד סביבת הבדיקה לא מוגדרת, תיקונים נעצרים במצב "ממתין להשלמת הגדרות".
- **חזרה לגרסה קודמת** אפשרית רק כל עוד הגרסה של הפנייה היא זו שרצה עכשיו. כך `החזר` על פנייה ישנה לא מוחק העלאות שבאו אחריה.
- **ממשק הניהול:** סיסמה, עוגייה חתומה (HttpOnly, SameSite=Strict), הגנת CSRF, הגבלת ניסיונות כניסה לפי כתובת וגם בסך הכול, ו-CSP קשיח.

**סיכון שנשאר:** Claude עצמו צריך את הטוקן שלו כדי לעבוד. לפי התיעוד של Claude Code, הטוקן מאפשר רק בקשות למודל. Claude לא מריץ קוד, ולכן הדרך לגנוב את הטוקן סגורה ככל שאפשר, אבל לא אפסית. אם יש חשש, אפשר להחליף את הטוקן בכל רגע ב-`claude setup-token` חדש.

## התקנה (פעם אחת)

### 1. שירות ב-Railway

כדאי פרויקט נפרד, `botix-repair`, כדי ששום דבר בו לא ייגע בשירותים של BotiX בטעות.

- **New Service ← GitHub Repo:** `miiuz0307-creator/wa-arms`
- **Branch:** `botix-repair`. הבוט עצמו לא נמצא בענף הראשי, ולכן עדכונים שלו לא מפעילים מחדש את BotiX.
- **Root Directory:** `repair`. ה-Dockerfile ייבנה אוטומטית.
- **+ New ← Database ← PostgreSQL.** את `DATABASE_URL` מחברים כ-Reference Variable.
- **Volume** בנתיב `/data`, לצילומי מסך ולעותקי עבודה.
- **Public Domain** לממשק הניהול.

### 2. משתני סביבה

| משתנה | חובה | מה זה |
| --- | --- | --- |
| `ADMIN_PASSWORD` | כן | סיסמה לממשק הניהול, לפחות 10 תווים |
| `SESSION_SECRET` | כן | מחרוזת אקראית ארוכה, לפחות 32 תווים. מצפינה את חיבור הוואטסאפ. לשמור עותק |
| `DATABASE_URL` | כן | מה-Postgres של Railway |
| `CLAUDE_CODE_OAUTH_TOKEN` | כן | ראו שלב 3 |
| `GITHUB_TOKEN` | כן | ראו שלב 4 |
| `RAILWAY_PROD_TOKEN` | כן | ראו שלב 5 |
| `RAILWAY_STAGING_ENV_ID`, `RAILWAY_STAGING_TOKEN` | כן | ראו שלב 6 |
| `STAGING_HEALTH_URLS` | מומלץ | כתובת ממשק ה-staging, לבדיקת תקינות |
| `PROD_HEALTH_URLS` | מומלץ | כתובת ממשק הייצור |
| `RAILWAY_STAGING_SERVICES` | רק אם צריך | JSON של מזהי השירותים ב-staging, אם הם שונים מהייצור |
| `CLAUDE_MODEL` | לא | למשל `opus` או `sonnet`. ברירת המחדל: של Claude Code |
| `APPROVAL_MINUTES` | לא | תוקף קוד האישור. ברירת מחדל 30 |
| `AUTO_ROLLBACK` | לא | `false` מבטל חזרה אוטומטית. ברירת מחדל `true` |

### 3. חיבור ל-Claude, בלי מפתח API

במחשב שבו Claude Code מותקן ומחובר למנוי שלך, מריצים:

```
claude setup-token
```

הפקודה מדפיסה טוקן שתקף לשנה. מדביקים אותו ב-Railway כ-`CLAUDE_CODE_OAUTH_TOKEN`. צריך מנוי Pro, Max, Team או Enterprise. השימוש נספר מהמכסה של המנוי.

### 4. טוקן GitHub מוגבל

GitHub ← Settings ← Developer settings ← Fine-grained tokens:
- **Repository access:** רק `wa-arms`
- **Permissions:** Contents (Read and write), Pull requests (Read and write). שום דבר אחר.

### 5. טוקן Railway לייצור

בפרויקט `wa-arms` ב-Railway ← Settings ← Tokens ← יצירת Project Token לסביבת **production**. הטוקן הזה מאפשר רק את הפרויקט הזה: קריאת לוגים, מעקב אחרי העלאות וחזרה לגרסה קודמת.

### 6. סביבת בדיקה (staging): חשוב לקרוא

בפרויקט `wa-arms` ← New Environment ← `staging`:
- השירותים `engine` ו-`web` ב-staging עוקבים אחרי הענף **`staging`**. הבוט דוחף אליו כל תיקון לפני האישור.
- ⚠️ **ה-engine של staging חייב מסד נתונים משלו,** פרויקט Supabase נפרד או Postgres ב-Railway, **ו-`SESSION_SECRET` משלו.** אם הוא יקבל את המשתנים של הייצור, הוא יתחבר לזרועות האמיתיות וישלח הודעות אמיתיות.
- אחרי שהסביבה קיימת: מעתיקים את מזהה הסביבה ל-`RAILWAY_STAGING_ENV_ID` ויוצרים Project Token ל-staging בשביל `RAILWAY_STAGING_TOKEN`.

### 7. חיבור

1. נכנסים לממשק הניהול עם `ADMIN_PASSWORD`.
2. "מספרים מאושרים" ← מוסיפים את המספר שלך כ**מאשר**.
3. לוח בקרה ← "חיבור WhatsApp" ← סורקים את ה-QR מהטלפון של **מספר הבוט** (הגדרות ← מכשירים מקושרים ← קישור מכשיר).
4. ברשימת "מוכנות המערכת" כל השורות צריכות להיות ✅.

## חיבור ב-QR: מגבלות וסיכונים

- **זה לא ממשק רשמי של WhatsApp.** החיבור עובד דרך Baileys, ספרייה שמחקה את WhatsApp Web. התנאים של WhatsApp לא מתירים לקוחות לא רשמיים, ולכן תמיד יש סיכון שהמספר ייחסם.
- **הסיכון כאן נמוך יחסית:** הבוט שולח מעט הודעות, רק למספרים מאושרים, לא מצטרף לקבוצות ולא שולח בתפוצה.
- **השתמשו במספר ייעודי.** לא אחת הזרועות ולא המספר הראשי שלך. אם הוא ייחסם, BotiX לא נפגע.
- **ניתוקים אפשריים:**
  - טלפון שלא מתחבר לאינטרנט כ-14 יום מנתק את המכשירים המקושרים.
  - "ניתוק כל המכשירים" בטלפון מנתק גם את הבוט.
  - עדכון של WhatsApp יכול לשבור את Baileys עד שמגיע תיקון לספרייה.
  - בכל המקרים האלה הממשק מראה "לא מחובר", ופשוט סורקים שוב.
- **קוד 403** אומר ש-WhatsApp חסם או הגביל את המספר. הבוט מפסיק לנסות כדי לא להחמיר את המצב.
- **קוד 440** אומר שהבוט רץ פעמיים, למשל בשני שרתים. הבוט עוצר.
- **אם צריך יציבות מלאה:** WhatsApp Cloud API הרשמי. הוא דורש אימות עסקי ב-Meta. רק `src/wa.js` יצטרך להשתנות.

## מגבלות ידועות

- **שינויי מסד נתונים לא מוחלים אוטומטית.** אם תיקון כולל קובץ ב-`supabase/migrations/`, הבוט מתריע על כך בסיכום, ואת ההחלה על Supabase עושים ידנית.
- **staging לא בודק שליחה אמיתית בוואטסאפ.** הוא בודק שהקוד נבנה, עולה ולא קורס.
- **אחרי חזרה לגרסה קודמת, השינוי עדיין נמצא בענף הראשי** עד שמאשרים את בקשת הביטול שהבוט פותח. עד אז, העלאה הבאה לענף הראשי תחזיר אותו.
- **הבוט מטפל בפנייה אחת בכל פעם.** השאר ממתינות בתור.
- **שימוש בטוקן מנוי בשרת:** בתיעוד של Claude Code לא מצאתי מגבלות שימוש שנכתבו במיוחד לשרת שרץ בלי השגחה. כדאי לבדוק את תנאי השימוש של Anthropic.
